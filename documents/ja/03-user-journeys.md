# 03 — ユーザージャーニー

各ジャーニーでは、まずハッピーパスを示し、続いてより重要な経路、すなわち何かが
うまくいかなかったときに何が起きるかを示します。ジャーニーは、その例外フローが
記載どおりに処理されて初めて完成します。

---

## J-01 — カタログを閲覧する

**アクター:** 買い物客
**ゴール:** 何が販売されているかを把握する。

**メインフロー**

1. 買い物客がストアフロントを開きます。
2. システムは、すべての商品について名称、説明、画像、価格、在庫数、評価を
   表示します。
3. 在庫が少ない商品は、それとわかるように明示されます。
4. 在庫がゼロの商品は売り切れとして表示され、追加できません。

**例外フロー**

| # | 状況 | 求められる挙動 |
|---|---|---|
| E1 | カタログを読み込めない | 明示的にエラーを表示する。店に商品が1つもないかのように、空のカタログを表示してはならない |
| E2 | 商品に評価がない | スコアなしで商品を表示する。ゼロとして表示してはならない |
| E3 | カタログが実際に空である | E1 とは区別して、その旨を明確に伝える |

**事後条件** — 何も変化していません。閲覧に副作用はありません。

---

## J-02 — カートに商品を追加する

**アクター:** 買い物客
**事前条件:** 商品に在庫があること。

**メインフロー**

1. 買い物客が商品を選び、追加します。
2. システムはカートに1個を追加するか、その商品の既存の明細行を1つ増やします。
3. カートの点数が即座に、目に見える形で更新されます。

**例外フロー**

| # | 状況 | 求められる挙動 |
|---|---|---|
| E1 | ページ読み込みからクリックまでの間に商品が売り切れた | 追加を拒否し、現在は売り切れである旨を買い物客に伝える |
| E2 | 追加すると在庫数を超える | 超過分を拒否し、あと何個購入可能かを伝える |
| E3 | カートを保存できない | 買い物客に伝える。保存されなかった商品が画面に表示されたままになってはならない |

---

## J-03 — カートを変更する

**アクター:** 買い物客

**メインフロー**

1. 買い物客がカートを開き、すべての明細行の数量と明細金額、および小計を
   確認します。
2. 買い物客が数量を編集するか、明細行を削除します。
3. 合計金額が即座に再計算されます。
4. 変更が保存されます。

**例外フロー**

| # | 状況 | 求められる挙動 |
|---|---|---|
| E1 | 入力された数量がゼロ、マイナス、または整数でない | 保存前に拒否し、何が許容されるかを示すメッセージを表示する |
| E2 | 数量が在庫数を超える | 拒否し、あと何個購入可能かを伝える |
| E3 | **同一のカートが同時に別の場所から変更された**（別のタブまたはデバイス） | 競合を検知する。マージするか、変更を適用できなかったことを買い物客に伝えるかのいずれかとする。**もう一方の変更を暗黙に上書きしてはならない** |
| E4 | カートを保存できない | 買い物客に伝え、入力内容を画面に残す |

**E3 に関する注記。** セッションのカートは共有状態です。同じカートを2つのタブで
開くことは、エッジケースではなく通常の顧客行動です。画面上でいったん受理された
変更が後から失われることは、変更が拒否されることよりも悪い事態です。

---

## J-04 — クーポンコードを適用する

**アクター:** 買い物客
**事前条件:** カートが空でないこと。

**メインフロー**

1. 買い物客がチェックアウト時に1つ以上のクーポンコードを入力します。
2. システムが各コードを検証します。
3. クーポンは、買い物客が入力した順序に依存しない **定義され公開された順序** で
   適用されます。
4. 適用されたクーポンとともに、新しい合計金額が表示されます。

**例外フロー**

| # | 状況 | 求められる挙動 |
|---|---|---|
| E1 | コードが未知または期限切れである | どのコードがなぜ拒否されたかを伝える。有効なコードは適用したままにする |
| E2 | 2つのコードを併用できない | その旨を伝え、どちらが適用されたかを明示する |
| E3 | クーポン額が小計を超える | 合計をゼロで下限打ち切りする。マイナスの合計を生成してはならない |

**ステップ3 に関する注記。** あるカートとあるコードの組み合わせに対して、合計
金額は毎回同じでなければなりません。コードを入力した順序にも、2人の買い物客の
うちどちらが入力したかにも左右されません。

---

## J-05 — 注文を実行する

**アクター:** 買い物客
**事前条件:** カートが空でなく、セッションが有効であること。

**メインフロー**

1. 買い物客がカートと合計金額を確認します。
2. 買い物客が注文を送信します。
3. システムは次を行います。
   a. すべての明細行を現在の在庫に対して検証する。
   b. 現在の価格と適用されたクーポンから合計金額を計算する。
   c. 配送料見積を取得する。
   d. 在庫を確保する。
   e. 注文を `confirmed` として作成する。
   f. 監査レコードを書き込む。
4. 注文番号と請求金額とともに確定画面が表示されます。
5. カートが空になります。

**例外フロー**

| # | 状況 | 求められる挙動 |
|---|---|---|
| E1 | **買い物客が複数回送信する**（ダブルクリック、リトライ、リロード） | 作成される注文はちょうど1件。同一の意図によるそれ以降の送信は元の注文を返し、再度請求しない |
| E2 | **2人の買い物客が最後の1個を同時に購入する** | ちょうど1人が成功する。もう一方には売り切れである旨を伝える。在庫がゼロを下回ることはない |
| E3 | 明細行がすでに存在しない商品を参照している | 商品名を明示した明確なメッセージとともに拒否する。想定外エラーとしない |
| E4 | 数量が不正である | 何も確保する前に拒否する |
| E5 | 配送料見積が遅い、または利用できない | これだけを理由に注文を失敗させない。タイムアウトを適用し、標準料金にフォールバックして処理を続行する |
| E6 | **チェックアウトを開いてから支払うまでの間にセッションが期限切れになった** | セッションが期限切れになったことを買い物客に伝え、カートをそのまま保持し、セッションを再確立した後に続行できるようにする。カートを決して破棄しない |
| E7 | **監査レコードを書き込めない** | 注文を顧客に確定として伝え **ない**。記録できない注文は発生しなかったものとする |
| E8 | 在庫確保より後のいずれかのステップが失敗する | 確保した在庫を解放する。存在しない注文に対して在庫が確定されたままになってはならない |

**成功時の事後条件** — `confirmed` 注文がちょうど1件存在し、在庫は注文数量
ちょうどの分だけ減少し、監査レコードがちょうど1件存在し、カートは空になって
います。

**失敗時の事後条件** — 注文は存在せず、在庫は変化せず、監査レコードもなく、
カートは手つかずのままで、買い物客は失敗したことを認識しています。

---

## J-06 — セッションが期限切れになる

**アクター:** 買い物客
**トリガー:** セッションが有効でなくなること。典型的には無操作状態が続いた後。

**メインフロー**

1. 買い物客がセッション期限切れ後に操作を行います。
2. システムは、セッションが一度も存在しなかったのではなく、**明確に** セッション
   が期限切れになったことを認識します。
3. 買い物客の手を煩わせることなく、セッションの再確立を試みます。
4. 再確立に成功した場合、元の操作がそのまま続行され、買い物客は何も気づきません。

**例外フロー**

| # | 状況 | 求められる挙動 |
|---|---|---|
| E1 | セッションを再確立できない | セッションが期限切れになったこと、**およびカートは無事であること** を買い物客に伝える。続行を促す |
| E2 | チェックアウトの途中で期限切れになる | E1 と同じ。カートと入力済みのクーポンコードは保持される |

**注記。** 「期限切れ」と「一度も認証されていない」は、対処法の異なる別々の問題
です。この2つを区別できないメッセージは、買い物客にどうすればよいのか分からない
状態を強いるものであり、欠陥として扱います。
